# Proactive Supervisor pilot: version 1

This is an artifact-only deployment profile for one tenant on one dedicated Linux VM. `compose.json` has no default services: every service requires the `authorized-staging` profile. The journal plugin under `plugins/supervisor_v1` is not installed. Do not enable enrollment until the separate B10 disposable-staging acceptance is complete and the tenant owner authorizes it.

## Topology and boundaries

- `writer` is the designated version 4 journal installation and canonical database. Its reviewed image includes the local `install.sh`, `src`, update path and source commit; it installs or upgrades `.journal` at startup, then starts `.journal/bin/journal serve` as uid 10001. The owner API and local CLI/hooks bind to `127.0.0.1:8421`. A separate owner UI listener binds only to `10.76.10.10:8423` on `journal_management`; host loopback port 18440 forwards to that management-only listener through an SSH or tenant-VPN tunnel. A separate TLS listener binds only to `10.76.20.10:8422` on `gateway_link`; its handler dispatches only the five token-checked supervisor service routes and refuses enrollment or ordinary owner API routes before routing. Gateway is not on `journal_management` and cannot reach either owner listener. The certificate must have DNS SAN `writer`; the Gateway verifies it using the tenant CA secret. The writer stores journal data in `writer_state` and Plan-driver device-auth state in `codex_driver_state`. Its fixed Plan launcher accepts requests only from the journal server's recorded PID and uid 10001, then starts numbered Codex Plan agents as uid/gid 10003 with no capabilities, no-new-privileges and a read-only container root. The server registers each Plan supervisor under its environment in `.journal/runtime/inboxes`; the broker assigns its socket at `/run/journal-plan-driver-supervisors/plan-<n>.sock`. The setgid directory is root:10031 mode 2770 and each socket is uid 10003 gid 10031 mode 0660; only the journal uid 10001 and Plan driver uid 10003 join group 10031. The driver writes its announcement only under its private runtime, never the owner's `.journal`, and the server never reads `CODEX_HOME`. An ACL grants the driver access to only the named Plan worktree; the journal service's ordinary identity cannot read the driver's auth volume. There is no separate login page in this private staging profile: Gateway uses only the bounded token-checked TLS routes, and live setup uses the owner's loopback CLI and owner-only management listener.
- `gateway` and its stdio client run as uid 1000. `build-gateway.sh` creates the local image tagged with `PROFILE_REVISION` from the pinned OpenClaw v2026.10.8 base digest in `manifest.json`; `Dockerfile.gateway` adds the Python runtime and `/opt/journal-supervisor/bin/journal-supervisor-bridge`. Compose only consumes this prebuilt image, and the smoke launcher keeps `--pull never --no-build`. The Gateway has its own `gateway_state` volume, a read-only event-reference spool, no journal database/source/worktree mount, and no Docker or host socket. The stdio shim starts the fixed loopback Anthropic Messages proxy; its metering state is stored under `gateway_state` and survives Gateway and shim restarts. Its port 18789 is private and is never published on the VM.
- The source-controlled journal plugin is a small event-reference bridge. `PluginServices` starts and stops it and `PluginHealth` probes its Unix health socket. It writes only task/check references to `supervisor_hints`; Gateway sees this volume read-only. Installation and creation of the `STAGING_AUTHORIZED` marker are separate owner/operator actions. Artifact packaging does neither.
- The bridge runs inside the journal environment supervisor, so the existing plugin lifecycle gives it the standard `JOURNAL_PLUGIN_TOKEN` and `JOURNAL_ROOT` environment. Its reviewed code does not use either value or open rows; this remains part of the trusted journal boundary. Gateway receives only the separately scoped supervisor credential and the read-only hint volume.
- The writer image pins `@openai/codex@0.165.0`. The image pre-creates `/var/lib/journal-codex` as uid/gid 10003 mode 0700, so a new `codex_driver_state` volume copies that ownership. The fixed `supervisor-codex-login` command must run as uid/gid 10003; it refuses a missing, linked, wrongly owned or wrongly permissioned home and never changes ownership. The owner approves the one-time device code in a browser. Codex stores `auth.json` and refresh tokens in the named volume; the volume is mounted into the writer, excluded from backup, and unreadable to uid 10001 by DAC. Plain `docker compose down` preserves it; never use `down --volumes` unless the owner intends to erase the login. If a volume was created by the failed root-owned login attempt before any device code was approved, inspect it and remove only that empty `journal-supervisor-smoke_codex_driver_state` volume before rebuilding; do not remove an authenticated volume. The owner main Codex session uses a separate `/data/home/.codex` login as uid 10001. The fixed `supervisor-live-setup` runs only on the designated writer after that owner session is active. It creates and approves a solo plan as that local owner, starts its Plan agent through the existing `PlanAgents` and `AgentLauncher` lifecycle, verifies its Codex session and running supervisor, then enrolls the bounded staging grant and writes the returned service token to `/run/journal_supervisor_credential` for the host setup script to install as the Gateway secret.
- The driver profile is packaged with the writer: the fixed launcher is the only Plan launch path in staging, the process drops its capability bounding set, and a per-worktree ACL grants uid 10003 access to that Plan worktree. The driver can also write its private Codex home; it has no other project-data write access. The selected packaging checks and Linux DAC probe do not establish the built container's actual process credentials, capability sets, mount visibility or restart behavior. B10 must prove those live properties and designated writer CLI/hook reachability on the disposable VM before customer enrollment; keep the gate false until then, and refuse enrollment if a probe fails.
- Every tenant gets a separate VM, Compose project name, volumes, repository credentials, API key, hook token, supervisor credential and backup repository. Do not connect this profile to another tenant or a shared Gateway.
- No OpenRig fleet or build worker launcher is packaged or required. If any existing worker is active, its required profile is uid/gid 10004, read-only root, no capabilities, `no-new-privileges`, only its own worktree writable, no secret mounts, and no network access beyond an identity-verified bound CLI/hook route. Enrollment must refuse before credentials or model calls unless every active worker passes the B10 probes.

### Ports and network policy

| Source | Destination | Port | Rule |
| --- | --- | ---: | --- |
| Owner/operator through SSH or tenant VPN | VM loopback to writer management listener | 18440 -> 10.76.10.10:8423 | Allowed only on loopback; no public bind |
| Gateway | Writer supervisor service | 10.76.20.10:8422 | Internal `gateway_link` only; TLS plus a token-checked service route |
| Gateway | Owner-only listeners | writer `gateway_link` address:8421 and 10.76.10.10:8423 | Owner API binds only to loopback; firewall denies both network destinations |
| Bridge and Gateway | OpenClaw Gateway | 18789 | Internal network only; never host-published |
| Gateway's loopback metering proxy | Anthropic Messages API | TCP 443 | Tenant VM firewall allows `api.anthropic.com` only; the configured OpenClaw provider URL is loopback and the proxy pins the upstream host and endpoints |
| Writer's Codex Plan driver | OpenAI API | TCP 443 | Tenant VM firewall allows `api.openai.com` only for Codex CLI; unlisted writer egress is denied |
| Backup | Selected encrypted repository | TCP 443 or repository-specific transport | Backup-only egress |
| Worker probe | Database, secret files, admin route, Gateway state | any | Denied; enrollment refuses any active worker outside the declared profile |

Compose networks are per project and `internal` where possible. `firewall-policy.fixture.json` is the operator-reviewable policy contract, not an applied firewall. On the disposable VM, B10 must realize its default-deny rules using the tenant-managed egress proxy/provider IP set and host firewall, with Gateway egress limited to `api.anthropic.com:443`, writer egress limited to `api.openai.com:443`, and backup egress limited to the exact repository endpoint recorded for that tenant. OpenClaw's configured base URL is the loopback proxy; the proxy only accepts Anthropic Messages requests, makes a Messages token-count preflight, and forwards to the fixed API origin. It records Anthropic's uncached input, cache-creation, cache-read and output token figures and fails closed if a usage figure is missing. Gateway reaches only the separate TLS supervisor listener on `gateway_link`; the owner API remains on loopback and the host-facing owner listener is bound only to `journal_management`. B10 must verify the owner listener is reachable through the host loopback tunnel, prove tokenless enrollment is refused on the Gateway listener, and record allowed and denied network probes from actual service identities. If an active worker cannot be proven to meet the restricted profile, enrollment must refuse before a credential or model request.

### Secret ownership and injection

Create a root-owned directory with mode 0700 outside the checkout and set both `TENANT_SECRET_SOURCE_DIR` and `TENANT_SECRET_DIR` to it in the operator's untracked `live-smoke.env`. The native SecretRun launcher runs as root and stages only the Gateway and backup secrets. File-backed Compose secrets retain host uid/gid/mode: Gateway secrets are `root:1000` mode 0440; backup secrets are `root:10005` mode 0440. Verify these owners and modes before launch. The task-111 OpenClaw config file must be `root:1000` mode 0440. Seed the writer volume from the owner-approved committed project export before starting it; do not mount a repository write token into the long-lived writer. The Compose secret map is the source of truth for secret mounts:

- `supervisor_anthropic_api_key`: tenant billing/project operator; mounted only into Gateway and read by its entrypoint. It belongs to the dedicated Anthropic API account; no subscription/OAuth profile or fallback is allowed.
- `openclaw_hook_token`: tenant operator; mounted only into Gateway.
- `journal_supervisor_credential`: journal owner/operator; mounted only to the Gateway stdio client. It must select one installation and be revocable. It is never the plugin token, local-person credential, owner cookie or a tenant selector.
- `restic_password`, `restic_repository`, `backup_object_store_credentials`: backup operator; mounted only into the backup service.

The Codex device login is not a Compose secret and is never supplied through SecretRun. After building the reviewed writer image, while services are off, the owner starts the one-time browser approval with:

```sh
docker compose --project-name journal-supervisor-smoke --env-file docs/supervisor/v1/live-smoke.env -f docs/supervisor/v1/compose.json --profile authorized-staging run --rm --no-deps --user 10003:10003 -it --entrypoint /usr/local/bin/supervisor-codex-login writer
```

The command accepts no arguments and must run as uid/gid 10003 into the persistent `codex_driver_state` volume. The owner opens the displayed URL on a trusted browser and approves the staged writer's device code. If the organization has disabled Codex CLI device-code authentication, its administrator must enable that sign-in method before staging. The journal server and smoke launcher fail closed without a private uid10003 `auth.json`; the launcher checks it as uid10003 in a one-shot writer container before starting either service. While the writer is running, reauthenticate with `docker compose --project-name journal-supervisor-smoke --env-file docs/supervisor/v1/live-smoke.env -f docs/supervisor/v1/compose.json --profile authorized-staging exec --user 10003:10003 -it writer supervisor-codex-login`. Refresh tokens remain in the named volume across ordinary Compose down/up cycles. Revoke the subscription session from the owner's account and remove the volume when retiring the staged writer. The owner main session has its own device login under `/data/home/.codex`; it does not read the Plan driver's volume.

The Gateway entrypoint reads its API key, hook token, revocable journal credential and writer TLS CA from files mounted only into Gateway. It exports the credential as `JOURNAL_SUPERVISOR_ADMISSION_TOKEN` and the CA path as `JOURNAL_SUPERVISOR_TLS_CA_FILE`; Compose sets `JOURNAL_SUPERVISOR_ADMISSION_URL` to `https://writer:8422` on `gateway_link`. The writer TLS certificate and private key are separate files mounted only into the writer as uid/gid 10001; the CA is mounted only into Gateway as uid/gid 1000. The tenant TLS operator provisions a certificate whose DNS SAN is `writer`, keeps the key and certificate host files `root:10001` mode 0440, and keeps the CA file `root:1000` mode 0440. Compose refuses startup when any TLS file is absent, and the bridge fails closed if the non-loopback TLS CA path is missing. The stdio proxy uses only the injected API key and forwards it to the fixed Anthropic origin; it does not accept a provider key, upstream URL or model from the agent. The backup entrypoint reads backup credentials inside the backup container. No secret value belongs in `compose.json`, `gateway-policy.fixture.json`, `.codex/config.toml`, an image layer or a journal record.

## Backup, restore and retention

The backup service runs as uid/gid 10005 with only `DAC_READ_SEARCH` added; `writer_state` and `gateway_state` are mounted read-only, and the service has no journal or Gateway network. It writes an encrypted snapshot every 15 minutes to the operator-selected repository. The writer volume is readable for backup by this constrained read-only identity; the Gateway state bind directory is pre-created as uid 1000, gid 10030, mode 0750 so both Gateway and the backup reader can traverse it. No write capability is granted to either source volume. The backup excludes journal runtime sockets/logs, `/data/secrets`, provider CLI credentials under the journal home, `/var/lib/journal-codex`, and the hint spool. It retains 7 daily snapshots and 4 weekly snapshots; a `final` tag is kept through pruning. The declared targets are RPO 1 hour and RTO 4 hours. A missing or older-than-one-hour successful snapshot blocks enrollment.

Run a one-shot snapshot with `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json --profile authorized-staging run --rm --no-deps -e BACKUP_ONCE=1 backup`. Restore with `-e RESTORE_SNAPSHOT=SNAPSHOT_ID` after replacing `SNAPSHOT_ID` with the reviewed snapshot id; the backup entrypoint writes only into `/restore-candidate`.

To restore, first activate the kill switch below and stop `writer`, `gateway` and `backup`. Run the backup image once with `RESTORE_SNAPSHOT=<snapshot>` so data is written only to `restore_candidate`; do not mount that directory into a running service. Verify the restic snapshot and database, inspect owner/plan/binding state read-only, and copy `/restore-candidate/data` and `/restore-candidate/gateway` into newly provisioned volumes with an operator-controlled, network-disabled one-shot copy process. Reapply the reviewed ownership and modes: journal runtime-owned files must be accessible to uid 10001, Gateway state to uid 1000:10030, and secret files must be re-injected from the secret owner rather than restored. Rotate the installation epoch and revoke all grants and credentials from before the restore. Keep writes disabled while doing these checks. Only after an owner/operator signs off may the restored writer volume replace the empty project-scoped volume and the services be started under a new B10 staging run. Restored Gateway sessions are not authority; the new epoch and credentials fence stale callbacks.

If the restore cannot be verified inside the 4-hour RTO, keep the old and candidate volumes offline, retain the last known-good snapshot and report the specific failed check. Never restore over a live writer.

## Grant revocation and operator kill switch

1. Stop the Gateway immediately with `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json --profile authorized-staging stop gateway`.
2. Have the owner revoke the grant using the checked enrollment-change route. If that route is unavailable, block `gateway_link` at the tenant firewall and stop the writer until revocation is available.
3. Disable `supervisor-v1` with `journal plugin disable supervisor-v1`, remove the plugin data marker `STAGING_AUTHORIZED`, then stop the journal environment supervisor. This stops the bridge through the existing plugin service lifecycle.
4. Revoke the `journal_supervisor_credential`; rotate the hook token and provider API key if exposure is suspected. Remove the secret files from the operator host only after replacement values are installed and verified.
5. Pause the plan as its owner. Preserve receipts and evidence read-only; do not reuse a prior run, grant, fence or restored installation epoch.

Rollback of a proposed write uses its verified journal receipt and current revisions. Preserve any owner-edited field and never delete or unassign a diagnostic that the ordinary driver has started. If rollback cannot prove its expected revision, leave the owner value intact and escalate.

## Authorized staging sequence

The profile is not a VM installer and does not assume that a prepared VM is operational. B10 performs these steps only in an owner/operator-authorized disposable tenant:

1. Provision a clean dedicated VM, private DNS for `writer`, SSH/VPN access, a tenant-specific Compose project, remote encrypted backup destination, host firewall and a root-owned secret directory with mode 0700. Have the tenant TLS operator place the writer certificate/key and CA files there with the manifest's exact owners and modes; the certificate SAN must include `writer`. Pre-create `GATEWAY_STATE_PATH` as uid 1000:gid 10030 mode 0750 and `RESTORE_CANDIDATE_PATH` as uid/gid 10005 mode 0700. Set both secret directory variables in `live-smoke.env` to the same path. Set `RUNTIME_SOURCE` to a clean checkout at `PROFILE_REVISION` and run `build-writer.sh` and `build-gateway.sh`; each requires a clean matching commit and removes its temporary context. The Gateway build archives only `src/supervisor_bridge`, `Dockerfile.gateway` and the bridge wrapper, then derives the local image from the pinned OpenClaw digest. This keeps `.journal`, `.codex`, `.claude`, tests, build caches and untracked files out of both Docker build contexts. Set `PROFILE_REVISION` to that exact commit in the owner-local `live-smoke.env`, so Compose resolves the already-built local tags while using `--pull never --no-build`. Before starting services, run the fixed device-auth bootstrap in the Secret ownership and injection section and approve its device code in a trusted browser. It stores the subscription auth and refresh tokens in `codex_driver_state`; ordinary `docker compose down` preserves that volume, which backup excludes. Do not use `down --volumes`, and do not stage an API key or use Secret 2 for Codex. Run `seed-project.sh` with an owner-approved clean project clone and its separate `PROJECT_REVISION`; it archives only the matching committed project checkout into an empty `writer_state` volume, excludes `.journal`, `.codex` and `.claude`, refuses common tracked secret/key paths, and does not copy untracked files. The script initializes `/data/project` as a `main` Git repository and creates its first commit as uid/gid 10001 with `PROJECT_REVISION` in the message. The owner must review tracked content for credentials before seeding. Record both exact source revisions, the writer build digest, derived Gateway digest and pinned base digest, OS/kernel, UID/GID map, network rules and secret owners.
2. Review `manifest.json` and `gateway-policy.fixture.json`; confirm the raw OpenClaw config supplied through `OPENCLAW_CONFIG_FILE` was built by task 111 and validated against the pinned schema. Confirm its only provider base URL is the loopback metering proxy and its model fallback list is empty. Refuse `latest` or tag-only external images, missing keys, unknown model cost bounds, fallback profiles or wildcard tool policies. The locally built Gateway tag must exactly match `PROFILE_REVISION`, and its derived digest must be recorded.
3. Run `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json config --quiet` and inspect every resolved mount, secret, port and network. Record the built writer and derived Gateway image digests; verify the Gateway's OpenClaw base digest and the backup image reference are pinned. Confirm all services remain off until the owner/operator separately launches `--profile authorized-staging`.
4. Start only the writer and prove `GET /journal/health` after a cold restart. The owner first signs in as uid/gid 10001 under `/data/home/.codex` with `docker compose --project-name journal-supervisor-smoke --env-file docs/supervisor/v1/live-smoke.env -f docs/supervisor/v1/compose.json --profile authorized-staging exec --user 10001:10001 --env CODEX_HOME=/data/home/.codex -it writer codex login --device-auth`. From a terminal on the designated VM, the owner starts a real main Codex session through the version 4 project command: `docker compose --project-name journal-supervisor-smoke --env-file docs/supervisor/v1/live-smoke.env -f docs/supervisor/v1/compose.json --profile authorized-staging exec --user 10001:10001 --env JOURNAL_ROOT=/data/project --env JOURNAL_PORT=8421 --env CODEX_HOME=/data/home/.codex -it writer /data/project/.journal/bin/journal codex --env main --yes --no-open`. Keep that session running. Only after the owner authorizes the staging grant, run `STAGING_AUTHORIZED=1 docs/supervisor/v1/setup-live-smoke.sh` as root. The fixed setup requires that live Codex owner session and no active worker; it creates and approves the solo plan, phase, task, deliberately failing `false` smoke check and diagnostic template through the owner CLI, starts the Plan agent through the ordinary plan lifecycle, waits for a real Codex session and running supervisor, then posts the 24,000 input / 8,000 output / 8 request, one-turn and one-dollar bounded-write grant to the local enrollment route. The intentionally failing check gives the supervisor one current failure episode to diagnose; it is limited to this live smoke setup. The host script copies the response token into the root secret directory as `root:1000` mode 0440 for the Gateway. This is a one-off authorized staging grant, not customer enrollment. If setup creates the grant but host token transfer or installation fails, stop the writer, revoke the provisional grant through the owner's journal UI, restart the writer to clear its `/run` token, and remove any partial host secret before retrying; if revocation cannot be confirmed, discard the staging writer volume and rebuild it. Cold-reboot the disposable VM and prove the designated writer returns healthy and the owner-started, bound Plan driver remains reachable from the designated node through its CLI and hook route. Identify the writer installation and bound environment from that node; do not use a developer laptop or manually prepared local process.
5. Install/enable the source plugin only after the owner authorizes staging and creates `STAGING_AUTHORIZED`. Prove plugin service start, health, restart and stop through `PluginServices`/`PluginHealth`; verify the 1,000-reference spool contains no row content and Gateway cannot write to it.
6. Prove the staged Plan process has uid/gid 10003, an empty capability bounding/effective/permitted set, `no_new_privs`, a read-only root, and write access only to its Codex home and its own Plan worktree. Prove uid10001 cannot read the Codex volume, and that a worker cannot use the launcher socket or reach private credentials/database ports. The package routes Plan Codex launches through a fixed local broker bound to the designated journal server PID and applies a uid10003 ACL only to the selected Plan worktree. Its artifact checks and Linux DAC probe do not establish the built container's actual process credentials, capability sets, mount visibility, restart behavior or designated-node route. B10 remains false until those live properties pass on the disposable VM; keep enrollment disabled until then. From Gateway, deny access to writer data/source/worktrees and host sockets. If any active worker fails its required uid/gid 10004, no-capability, no-new-privileges, no-secret profile, prove enrollment refuses before any credential or model call.
7. Prove network allowlists and per-tenant isolation with positive and negative connect probes, including a TLS-verified request from Gateway to `https://writer:8422` and a tokenless POST to `/_supervisor/v1/enrollment` that returns 403. Prove Gateway cannot connect to the writer's `gateway_link` address on 8421 or to `10.76.10.10:8423`. Verify the host loopback tunnel reaches owner listener 8423, and local CLI/hooks reach 8421. Then restart Gateway and writer and verify their health. Route a deterministic command and hook from the designated node; verify the same admission path is used for timer and event hints and an empty reconciliation makes no model call.
8. Run a backup, restore it into `restore_candidate` with writes disabled, verify the snapshot and installation identity, copy into fresh volumes with the writer still stopped, rotate the epoch and demonstrate stale-grant rejection. Record actual backup age, elapsed restore time, secret mount inventory, UID/GID probes, network probe results, and service health. Acceptance fails if RPO/RTO targets or any denial probe is missed.
9. Keep enrollment disabled until all evidence is reviewed and the tenant owner separately authorizes it. Customer plugin installation/enabling and grant creation are not part of artifact packaging.
