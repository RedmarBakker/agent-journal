# Proactive Supervisor pilot: version 1

This is an artifact-only deployment profile for one tenant on one dedicated Linux VM. `compose.json` has no default services: every service requires the `authorized-staging` profile. The journal plugin under `plugins/supervisor_v1` is not installed. Do not enable enrollment until the separate B10 disposable-staging acceptance is complete and the tenant owner authorizes it.

## Topology and boundaries

- `writer` is the designated journal installation and canonical database. Its source is built from the reviewed repository checkout. It uses the existing `docker/Dockerfile`, runs the journal as uid 10001, persists only to the project-scoped `writer_state` volume and has no public listener. Port 8421 is private to `gateway_link`; the owner UI is reachable only at host loopback port 18440 through an SSH or tenant-VPN tunnel.
- `gateway` and its stdio client run as uid 1000. The image is the immutable GHCR manifest digest in `manifest.json`, corresponding to OpenClaw v2026.10.8 and the reviewed source commit. It has its own `gateway_state` volume, a read-only event-reference spool, no journal database/source/worktree mount, and no Docker or host socket. Its port 18789 is private and is never published on the VM.
- The source-controlled journal plugin is a small event-reference bridge. `PluginServices` starts and stops it and `PluginHealth` probes its Unix health socket. It writes only task/check references to `supervisor_hints`; Gateway sees this volume read-only. Installation and creation of the `STAGING_AUTHORIZED` marker are separate owner/operator actions. Artifact packaging does neither.
- The bridge runs inside the journal environment supervisor, so the existing plugin lifecycle gives it the standard `JOURNAL_PLUGIN_TOKEN` and `JOURNAL_ROOT` environment. Its reviewed code does not use either value or open rows; this remains part of the trusted journal boundary. Gateway receives only the separately scoped supervisor credential and the read-only hint volume.
- The ordinary plan driver must remain the already owner-started `codex` Plan agent bound to this installation and environment. Its required profile is uid/gid 10003, read-only root, no capabilities, `no-new-privileges`, one writable owner-bound plan worktree, and no writer, Gateway-state or provider-secret mount. Only the separately issued `codex_driver_credentials` may be mounted after a supported adapter exists. The current `AgentLauncher` starts its CLI as the environment supervisor identity; it does not enforce this profile. Enrollment remains off. B10 must prove the actual launched process has the restricted execution profile and can reach the designated writer through the existing CLI/hook route. If that proof fails, return the precise launcher/profile deficiency and do not enroll.
- Every tenant gets a separate VM, Compose project name, volumes, repository credentials, API key, hook token, supervisor credential and backup repository. Do not connect this profile to another tenant or a shared Gateway.
- No OpenRig fleet or build worker launcher is packaged or required. If any existing worker is active, its required profile is uid/gid 10004, read-only root, no capabilities, `no-new-privileges`, only its own worktree writable, no secret mounts, and no network access beyond an identity-verified bound CLI/hook route. Enrollment must refuse before credentials or model calls unless every active worker passes the B10 probes.

### Ports and network policy

| Source | Destination | Port | Rule |
| --- | --- | ---: | --- |
| Owner/operator through SSH or tenant VPN | VM loopback to writer | 18440 -> 8440 | Allowed only on loopback; no public bind |
| Gateway and designated execution profile | Writer supervisor/CLI service | 8421 | Internal network only; the writer authorizes each route and credential |
| Bridge and Gateway | OpenClaw Gateway | 18789 | Internal network only; never host-published |
| Gateway | OpenAI API | TCP 443 | Tenant VM firewall allows `api.openai.com` only |
| Backup | Selected encrypted repository | TCP 443 or repository-specific transport | Backup-only egress |
| Worker probe | Database, secret files, admin route, Gateway state | any | Denied; enrollment refuses any active worker outside the declared profile |

Compose networks are per project and `internal` where possible. `firewall-policy.fixture.json` is the operator-reviewable policy contract, not an applied firewall. On the disposable VM, B10 must realize its default-deny rules using the tenant-managed egress proxy/provider IP set and host firewall, with Gateway egress limited to `api.openai.com:443` and backup egress limited to the exact repository endpoint recorded for that tenant. Container network membership alone is not a port firewall: in particular, Gateway must fail to connect to writer port 8440 and any database port even though it shares `gateway_link`. B10 records the applied rules and both allowed and denied probes from the actual service identities. If an active worker cannot be proven to meet the restricted profile, enrollment must refuse before a credential or model request.

### Secret ownership and injection

Create a root-owned directory with mode 0711 outside the checkout and point `TENANT_SECRET_DIR` at it in the operator's untracked environment file. File-backed Compose secrets retain host uid/gid/mode, so provision each secret file root-owned and readable only by its receiving service group: Gateway secrets are `root:1000` mode 0440; backup secrets are `root:10005` mode 0440. Keep the directory non-listable and verify these numeric owners and modes before launch. The task-111 OpenClaw config file must be `root:1000` mode 0440. Seed the writer volume from the owner-approved committed project export before starting it; do not mount a repository write token into the long-lived writer. The Compose secret map is the source of truth for mounts:

- `supervisor_openai_api_key`: tenant billing/project operator; mounted only into Gateway and read by its entrypoint. It belongs to the dedicated Platform API project; no subscription/OAuth profile or fallback is allowed.
- `openclaw_hook_token`: tenant operator; mounted only into Gateway.
- `journal_supervisor_credential`: journal owner/operator; mounted only to the Gateway stdio client. It must select one installation and be revocable. It is never the plugin token, local-person credential, owner cookie or a tenant selector.
- `restic_password`, `restic_repository`, `backup_object_store_credentials`: backup operator; mounted only into the backup service.
- `codex_driver_credentials`: plan owner; must be available only to the restricted execution identity. Current launcher packaging does not provide that boundary, so this secret is deliberately absent from the Compose secret map and enrollment stays disabled until B10 verifies a supported injection path.

The Gateway entrypoint reads its API key, hook token and revocable journal credential from files mounted only into Gateway, then exports them for the pinned Gateway and its configured stdio client. The backup entrypoint reads backup credentials inside the backup container. No secret value belongs in `compose.json`, `gateway-policy.fixture.json`, `.codex/config.toml`, an image layer, a journal record or a backup.

## Backup, restore and retention

The backup service runs as uid/gid 10005 with only `DAC_READ_SEARCH` added; both source volumes are mounted read-only, and the service has no journal or Gateway network. It writes an encrypted snapshot every 15 minutes to the operator-selected repository. The writer volume is readable for backup by this constrained read-only identity; the Gateway state bind directory is pre-created as uid 1000, gid 10030, mode 0750 so both Gateway and the backup reader can traverse it. No write capability is granted to either source volume. The backup excludes journal runtime sockets/logs, `/data/secrets`, provider CLI credentials under the journal home, and the hint spool. It retains 7 daily snapshots and 4 weekly snapshots; a `final` tag is kept through pruning. The declared targets are RPO 1 hour and RTO 4 hours. A missing or older-than-one-hour successful snapshot blocks enrollment.

Run a one-shot snapshot with `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json --profile authorized-staging run --rm --no-deps -e BACKUP_ONCE=1 backup`. Restore with `-e RESTORE_SNAPSHOT=SNAPSHOT_ID` after replacing `SNAPSHOT_ID` with the reviewed snapshot id; the backup entrypoint writes only into `/restore-candidate`.

To restore, first activate the kill switch below and stop `writer`, `gateway` and `backup`. Run the backup image once with `RESTORE_SNAPSHOT=<snapshot>` so data is written only to `restore_candidate`; do not mount that directory into a running service. Verify the restic snapshot and database, inspect owner/plan/binding state read-only, and copy `/restore-candidate/data` and `/restore-candidate/gateway` into newly provisioned volumes with an operator-controlled, network-disabled one-shot copy process. Reapply the reviewed ownership and modes: journal runtime-owned files must be accessible to uid 10001, Gateway state to uid 1000:10030, and secret files must be re-injected from the secret owner rather than restored. Rotate the installation epoch and revoke all grants and credentials from before the restore. Keep writes disabled while doing these checks. Only after an owner/operator signs off may the restored writer volume replace the empty project-scoped volume and the services be started under a new B10 staging run. Restored Gateway sessions are not authority; the new epoch and credentials fence stale callbacks.

If the restore cannot be verified inside the 4-hour RTO, keep the old and candidate volumes offline, retain the last known-good snapshot and report the specific failed check. Never restore over a live writer.

## Grant revocation and operator kill switch

1. Stop the Gateway immediately with `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json --profile authorized-staging stop gateway`.
2. Have the owner revoke the grant using the checked enrollment-change route. If that route is unavailable, block `gateway_link` at the tenant firewall and stop the writer until revocation is available.
3. Disable `supervisor-v1` with `journal plugin disable supervisor-v1`, remove the plugin data marker `STAGING_AUTHORIZED`, then stop the journal environment supervisor. This stops the bridge through the existing plugin service lifecycle.
4. Revoke the `journal_supervisor_credential`; rotate the hook token and provider API key if exposure is suspected. Remove the secret files from the operator host only after replacement values are installed and verified.
5. Pause the plan as its owner. Preserve receipts and evidence read-only; do not reuse a prior run, grant, fence or restored installation epoch.

Rollback of a proposed write uses its verified journal receipt and current revisions. Preserve any owner-edited field and never delete or unassign a diagnostic that the ordinary driver has started. If rollback cannot prove its expected revision, leave the owner value intact and escalate.

## Authorized staging sequence

The profile is not a VM installer and does not assume that a prepared VM is operational. B10 performs these steps only in an owner/operator-authorized disposable tenant:

1. Provision a clean dedicated VM, private DNS, SSH/VPN access, a tenant-specific Compose project, remote encrypted backup destination, host firewall and root-owned secret files. Pre-create `GATEWAY_STATE_PATH` as uid 1000:gid 10030 mode 0750 and `RESTORE_CANDIDATE_PATH` as uid/gid 10005 mode 0700. Set `RUNTIME_SOURCE` to a clean checkout at `PROFILE_REVISION` and run `build-writer.sh`; it creates a temporary context containing only `src`, the existing `docker/Dockerfile` and its two required startup scripts, then removes it. This keeps `.journal`, `.codex`, `.claude`, tests, build caches and untracked files out of the Docker build context. Run `seed-project.sh` with an owner-approved clean project clone and its separate `PROJECT_REVISION`; it archives only the matching committed project checkout into an empty `writer_state` volume, excludes `.journal`, `.codex` and `.claude`, refuses common tracked secret/key paths, and does not copy untracked files. The owner must review tracked content for credentials before seeding. Record both exact source revisions, the writer build digest, Gateway digest, OS/kernel, UID/GID map, network rules and secret owners.
2. Review `manifest.json` and `gateway-policy.fixture.json`; confirm the raw OpenClaw config supplied through `OPENCLAW_CONFIG_FILE` was built by task 111 and validated against the pinned schema. Refuse `latest`, tag-only images, missing keys, unknown model cost bounds, fallback profiles or wildcard tool policies.
3. Run `docker compose -p "$TENANT_PROJECT" -f docs/supervisor/v1/compose.json config --quiet` and inspect every resolved mount, secret, port and network. Record the built writer image digest and verify it was built from `PROFILE_REVISION`; verify the Gateway and backup image references are digest-pinned. Confirm all services remain off until the owner/operator separately launches `--profile authorized-staging`.
4. Start only the writer and prove its health after a cold restart. Cold-reboot the disposable VM and prove the designated writer returns healthy and the owner-started, bound Plan driver remains reachable from the designated node through its CLI and hook route. Identify the writer installation and bound environment from that node; do not use a developer laptop or manually prepared local process.
5. Install/enable the source plugin only after the owner authorizes staging and creates `STAGING_AUTHORIZED`. Prove plugin service start, health, restart and stop through `PluginServices`/`PluginHealth`; verify the 1,000-reference spool contains no row content and Gateway cannot write to it.
6. Prove Gateway and uid/gid 10003 execution identity filesystem access with allowed and denied reads. From Gateway, deny access to writer data/source/worktrees and host sockets. From a worker probe, deny reads of private credentials/database and connections to private admin ports. If any active worker fails, prove enrollment refuses before any credential or model call.
7. Prove network allowlists and per-tenant isolation with positive and negative connect probes, then restart Gateway and writer and verify their health. Route a deterministic command and hook from the designated node; verify the same admission path is used for timer and event hints and an empty reconciliation makes no model call.
8. Run a backup, restore it into `restore_candidate` with writes disabled, verify the snapshot and installation identity, copy into fresh volumes with the writer still stopped, rotate the epoch and demonstrate stale-grant rejection. Record actual backup age, elapsed restore time, secret mount inventory, UID/GID probes, network probe results, and service health. Acceptance fails if RPO/RTO targets or any denial probe is missed.
9. Keep enrollment disabled until all evidence is reviewed and the tenant owner separately authorizes it. Customer plugin installation/enabling and grant creation are not part of artifact packaging.

`tests/test_supervisor_runtime_packaging.py` checks the manifest, inert fixture, secret/mount boundaries and the uninstalled plugin package without installing or launching a deployment service. It does not replace the disposable-staging checks above. This checkout has not run a viewer build, installed a service, started a VM or performed staging probes.
