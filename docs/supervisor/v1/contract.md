# Proactive Supervisor integration contract, version 1

Florence for the orchestrator, task 103, 29 October 2026. Implements the contract-planning portion of approved plan 3 and refines journal doc 7. This is a versioned specification and inert fixture set. It installs nothing, starts nothing and contains no executable tests. ## Status and scope

The first supported deployment has one dedicated Linux VM per tenant, one always-on designated journal writer installation, one already approved started journal plan, its eligible current phase and its existing owner-started ordinary Plan agent. The first supported driver provider is `codex`. Journal, not OpenClaw, owns tasks, phase links, grants, observations, episode identity, admission, reservations and action receipts.

The useful loop is: capture a genuine existing verification failure or stall; qualify one episode; admit one bounded judgment turn; reuse or add one eligible read-only diagnostic in the same current phase; save an advisory priorities explanation and, when justified, shorten the enrolled check interval; verify those writes; then measure independent useful evidence. A no-op or escalation is a valid outcome. Repeated failures without genuine recovery remain the same episode. Supervisor-created notes and task creation do not establish progress.

The missing adapters are specified here rather than represented as existing interfaces. The private routes and `journal_supervisor.*` tools below do not exist merely because this document names them. Task 106 owns journal action admission; task 104 owns authority/authentication; task 105 owns durable observation capture; task 108 owns normal-driver pickup; task 111 owns the small runtime/MCP transport adapter. Later implementation must project the same contract through those origins. The existing journal terminal supervisor in `src/supervisor` is a different component from this product supervisor and is not replaced.

## One writer and ordinary driver topology

The designated journal server and its database are the canonical writer and check-observation origin on the tenant VM. Team sync is not an observation feed: current Entries and latest check results are local. OpenClaw's Gateway and stdio client shim have their own state and restricted service connection, with no journal database/source/worker-worktree mount, host socket or journal owner cookie. The journal management controller remains inside journal's domain boundary.

The OpenClaw stdio shim starts the loopback provider proxy before serving MCP. The complete pinned provider config names only that proxy, with no model fallback; the run gate also checks the configured route and proxy health before sending the reference-only hook. The proxy takes its run identity and grant limits from the durable bridge state populated from the admitted server reference and the authenticated grant snapshot. It counts exact input tokens before generation, clamps each output limit to the remaining grant, counts every upstream request and retry, requires input/output/cache usage on each completed response, and fails closed on an uncertain request or missing usage. Its durable totals are attached to the bridge's local read-back receipt summary. This is source and focused-test evidence; the canonical Journal receipt and a live provider turn remain staging proofs.

Use separate unprivileged execution identities for the journal service/management server, Gateway/client shim and execution side. The stdio shim is the Gateway's restricted client; it does not need the journal service's identity. Any execution worker must be in its restricted identity/container with no read access to Gateway state, provider or service credentials, or journal database and no management/admin network access. Different tenants receive separate VMs, volumes, credentials and network/backup policies. No customer chat channel or cross-agent routing is enabled in OpenClaw.

The existing normal Plan-agent path is reused:

1. `PlanAgents.started` checks the plan-agent switch, resolves/creates the plan environment, binds the plan, prepares a `LeadingPlan` agent and launches through `AgentEnvironments` (`features/plans/support/plan_agents.py:40`). Enrollment does not perform any of these start operations.
2. `AgentEnvironments.prepared` creates an `AgentRole.MAIN` row. `provider` uses the starter's provider, otherwise the configured default; `launched` resumes the saved session through that provider and `AgentLauncher.start_in_worktree` (`agent_environments.py:36`, `:39`, `:43`). Enrollment requires the existing row to say `codex`; it never relies on or triggers the default-provider fallback.
3. `PlanOwners.number` resolves the plan environment owner, then the bound driving environment owner for a hub plan. No owner means enrollment is refused (`plan_owners.py:15`). `AgentEnvironments.visible` preserves the source environment's team/private visibility rather than inventing new chat membership.
4. Driver commands continue through the existing journal CLI shim/controller and ordinary identity/launch proof. `http/controllers/cli.py:34` already receives argv from the shim and validates caller identity. The supervisor service credential has no access to this broad surface.
5. `PlanBindings` gives one local driving environment and an ended-drive refusal (`plan_bindings.py:24`, `:27`, `:43`). Enrollment binds to this exact driver/environment and designated installation, rather than trusting caller-selected environment headers.

The existing launcher does not by itself prove a separate OS identity/container, least-privilege mounts or unattended CLI/hook reachability. The pilot deployment profile must demonstrate its fixed execution boundary and the normal driver's communication with this same writer while private database/credential mounts remain inaccessible. Normal CLI/hook access must not open the new management route; private routing and authentication enforce that distinction. No generic remote executor or second journal task runner is introduced. If the deployment cannot preserve the ordinary launcher path with the required isolation, live enrollment is blocked and the precise launcher/profile deficiency is returned to main.

There is no blanket dependency on OpenRig tasks 29/30 or completion of plans 1/2. This topology uses the already supported ordinary launcher/provider/session path. A specific missing provider/session or execution-identity boundary may block the corresponding deployment/pickup acceptance proof, but it does not block provider-independent authority, observation or admission work. The main-supplied merged baseline from task 102 remains the integration baseline; no unaccepted seat runner, sidebar or board is assumed present.

## Version 1 schemas and service boundary

[contract.schema.json](contract.schema.json) is the normative closed structural schema, version `1`, with exact named `$defs`; [fixtures.json](fixtures.json) contains inert positive shapes and semantic negative cases. Structural validity never substitutes for ownership, relationship, revision or grant validation. All row IDs are canonical local `row_id` values in the server-selected scope, not viewer labels. Time fields are server Unix milliseconds; monetary amounts are integer micro-USD. Identifiers and revisions are opaque, bounded strings unless the schema says integer.

The following routes are the frozen proposed adapter contract, not current journal endpoints:

| Boundary | Request and result | Actor and purpose |
| --- | --- | --- |
| `POST /_supervisor/v1/enrollment` | `EnrollmentRequest` -> `Grant` | Authenticated actual owner only; server derives owner/scope/driver. Owner-only change uses the checked route below, not generic Entry CRUD. |
| `POST /_supervisor/v1/enrollment/change` | `GrantChangeRequest` -> `Grant` | Actual owner only, current grant-version CAS; revoke or replace through checked enrollment validation. |
| `POST /_supervisor/v1/admit` | `AdmissionRequest` -> `AdmissionResult` | Fixed bridge only. Credential selects the one enrollment. Timer and hint share this path; no model-selected tenant/plan/budget. |
| `POST /_supervisor/v1/observe` | `ObserveRequest` -> `ObserveResult` (`Run`, `Snapshot`, `ObservationPage`, server time) | Service actor, admitted run/epoch/fence. Page cursor is scoped and opaque. The complete snapshot uses the same `Grant`, row-reference/revision and freshness shapes; do not expose a raw database query. |
| `POST /_supervisor/v1/apply` | `ActionRequest` -> `Receipt` | Service actor. Atomically validate and apply the one typed bundle, or store a non-applied rejection/conflict/proposal. |
| `POST /_supervisor/v1/receipt` | `ReceiptRequest` -> canonical `Receipt` and later linked verification evidence | Scoped read, including after a lost response. Receipt state never grants authority to repeat a mutation. |

`ObserveResult` contains the closed `Snapshot`, including canonical grant/plan revision/state/approval/current phase, binding revision, live driver identity/provider/session presence and current holder, explicit owner/phase gates, existing diagnostic and eligible task IDs, enrolled check revisions/command hashes/intervals and write-eligibility reasons. `ObservationPage` carries the heartbeat/watermark, bounded evidence and cursor. `writable=false` is expected in shadow even when ordinary work is eligible. Task 111 must not expand these records into a generic arbitrary-row endpoint. Task 104 is the source of credential-derived identity; requests have no tenant/environment selector. Missing, bad, revoked or mismatched credentials get 401/403 before `Identity.build` can fall back to the local person (`http/support/identity.py:18`). The machine is attributed as the enrolled plugin actor; protected control Entries cannot be forged through generic Entry writes.

Enrollment is phase-specific. It includes the current phase row/number/revision, plan/binding revisions, explicit enrolled check IDs/command hashes/baselines, template revision, capability decisions, finite budgets, expiry and mode. The canonical `Grant` adds actual owner, installation scope and driver. Scope includes tenant/project/manager/writer/installation epoch, but these are deployment/enrollment identifiers to add, not a claim that existing journal has a ready-made tenant authorization model.

An authoritative revision is an opaque server token over relevant canonical object fields, relationship membership/order and gate/binding state. It must detect intervening relevant owner edits, including changes subsequently restored to old values; a model timestamp or content hash alone is insufficient. This is an adapter requirement, not an existing universal revision column. The implementation must extend/reuse the journal mutation/Entry origin to supply it and recheck it inside the transaction.

`ActionRequest` carries the journal-issued run/episode/action references, epoch/fence, grant version, durable observation references, expected revisions and a bounded typed operation list. It cannot contain arbitrary CLI, shell, commands, routes, raw settings maps, tenant selectors or grant edits. Rationale is bounded explanation, not private chain of thought. A new diagnostic takes template ID/revision and evidence IDs only; its executable instructions cannot come from external output.

`Receipt` separates `status` (`proposed`, `applied`, `conflicted`, `rejected`), deterministic verification and measured outcome. It includes canonical intent hash, actor/grant/run/scope/fence, evidence references, proposed operations and actual affected refs/diffs. Shadow receipts have no actual mutations and `verification=not_applied`. The runtime/provider/profile/config/usage evidence is linked through the decision-run record, owned by the bridge/journal admission path, not supplied by the model. `verified` means read-back matched, while `useful_evidence` requires independent task/check progress.

## Admission and durable action compatibility with task 106

This section is the shared semantic boundary for Lamport. It does not prescribe a second admission implementation or preempt his internal module/class names. Task 111 may map those internal types to the version 1 wire records; it must not reproduce their validation, leases or idempotency in the bridge. Internal Entry kind names remain task 106's implementation detail. All durable records live in journal Entries and existing work rows.

The trusted journal caller supplies resolved credential scope, current protected grant, eligibility/revision facts and an adopted finite budget envelope. None can be accepted from model input as trusted context. A timer/hint admission checks those facts and authoritative episode identity, skips empty/stale/owner-gated/overlapping work, then transactionally reserves the conservative maximum cost and one turn before returning `Run`. `Run` includes journal-issued episode/pending-action/run IDs, grant version, current installation epoch, increasing fence, lease expiry and reservation reference. An internal admission test may provide deterministic trusted fixtures without any Gateway/provider or HTTP server.

Use `Connection.transaction` (`BEGIN IMMEDIATE`) and the `Entries.recorded` idempotency origin. Repeated delivery to the same scope/action/intent returns the canonical outcome. A different normalized intent for the same action ID is rejected. Normalization binds protocol version, scope/installation, grant version, episode/evidence generation, exact operations and expected revisions; exclude delivery timestamps, transport retry IDs and rationale prose. Sort unique revision/observation references canonically; reject duplicate operations targeting one managed field, unknown fields, malformed numbers and nonfinite values. New or changed intent gets a journal-issued action reference linked to the prior attempt and still consumes episode limits.

The version 1 intent object has exactly protocol_version, scope, grant_id, grant_version, plan_id, episode_id, evidence_generation, observation_ids, expected_revisions and operations, resolved from trusted grant/episode context plus the checked action. Sort unique observation IDs lexicographically, expected revisions by (ref.table, ref.id), and operations by (kind, target table, target ID); a check operation targets checks/check_id, the others plans/plan_id. Normalize priorities text to LF and trim its outer whitespace before both saving and hashing; other strings remain exact. Serialize UTF-8 JSON with sorted object keys, no insignificant whitespace and unescaped non-ASCII, canonical decimal integers, and no floats/nonfinite values; SHA256 those bytes. Do not include run_id, fence, action_id or rationale in this semantic hash; validate their separate journal/auth/lease bindings. Task 106 owns this normalization origin; the bridge must call it rather than maintain another hasher.

Equivalent diagnostic creation is also deduplicated by episode/template identity, independent of model wording.

The apply order is: authenticate/derive scope and reject an obsolete installation epoch; normalize and find a prior action; for the same authorized retained action return its bound receipt without reapplying; for new work validate current grant/mode/revocation, live lease/fence, budgets, current phase/gates, expected revisions and the entire bundle; apply through existing domain operations and append the applied receipt in one transaction. A prior receipt is a read result, not a renewal of write authority. An old-epoch callback is rejected after restore; an authorized owner may inspect its retained evidence separately. A conflicted/rejected action ID cannot silently become an applied action after a later edit.

No remote model call, plugin hint, command execution or check run occurs inside this transaction. A crash before commit leaves no domain changes or applied receipt. Commit plus lost response returns the original IDs on replay. Lease expiry/reclaim advances the fence and prevents a late uncommitted claimant from writing. The observer/verifier later records matched/superseded effects and CAS rollback under the current grant; a changed owner field is preserved and an assigned diagnostic is never deleted as rollback.

Unknown price/runtime bounds/usage fail closed. Reserve conservatively before admission; an ambiguous timeout does not refund unknown spend. Usage settlement cannot permit the model to raise caps or self-certify a cheaper route. Task 106 can implement and test this arithmetic/control boundary independently; task 111 must establish the trustworthy finite runtime envelope and actual usage input before live model admission is allowed. There is no parallel adapter ledger.

At this freeze, the attempted live notification to worker 51 was refused because its running Codex session has no inbox. His inspected worktree had not yet exposed an admission module/API to map. This specification therefore freezes shared semantics and external shapes, while explicitly marking internal signature/kind mapping as unconfirmed. Main must hand this section and the fixture shapes to Lamport; once his implementation is available, compare its trusted context, units, replay order and fence semantics before wiring task 111. Do not call an unreviewed internal signature an existing interface.
